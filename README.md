# Kiara Live token gateway

This service is a separate, private Gemini Live ephemeral-token issuer. Keep it outside `kiara-server`. The primary Kiara backend remains responsible for user authentication, Redis admission, quotas, and session metering; it signs a short-lived internal request only after those checks pass. This gateway does not expose a user-facing authentication route or return the Gemini API key.

## Deploy

1. Deploy this folder as its own Node.js 20+ service with `npm ci` and `npm start`. For local development/test only, startup loads this folder's `.env` file without overriding variables already set in the process. Production must set `NODE_ENV=production` in the service manager and inject secrets there; production startup does not load `.env`.
2. Set one to ten unique `GEMINI_API_KEY_1` … `GEMINI_API_KEY_10` credentials (or the legacy `GEMINI_API_KEY` for slot 1), `KIARA_GEMINI_PROJECT_ID`, `KIARA_LIVE_SYSTEM_INSTRUCTION_SHA256`, `KIARA_GATEWAY_HMAC_SECRET` (at least 32 random bytes), and `REDIS_URL`. Store keys and secrets in the host's secret manager/environment, not files or source control. `GEMINI_CREDENTIAL_N_ENABLED` explicitly enables or disables each slot; a configured slot is enabled by default unless its flag is false. All enabled keys must belong to the same Google project.
3. Configure `KIARA_PROJECT_REQUESTS_PER_MINUTE`, `KIARA_GATEWAY_MAX_CONCURRENT`, and `KIARA_PROJECT_QUOTA_COOLDOWN_MS` against the actual Google project quota. All gateway replicas must use the same project ID and Redis deployment: atomic Redis scripts enforce one shared project request budget, active-token concurrency cap, and 429 cooldown. Start with one gateway replica for initial staging, then verify multi-replica Redis behavior before scaling. Admission is fail-closed when Redis is unavailable.
4. Expose `/healthz` over HTTPS. Only the authenticated primary backend should be able to reach `/internal/v1/live-token`; the endpoint also requires a timestamped HMAC signature and one-time Redis nonce.
5. Configure the primary backend with `KIARA_LIVE_GATEWAY_URL=https://<private-gateway-host>` and the same `KIARA_LIVE_GATEWAY_HMAC_SECRET`. Keep the gateway URL private and use HTTPS in production.
6. Deploy the primary backend change before directing Live-token traffic to the gateway. Leave the URL unset to keep the existing direct-provider path.

The credential validator accepts the legacy standard API-key form (`AIza...`) and the newer AI Studio authorization-key form (`AQ....`). Google's API-key documentation describes both key types, but does not define a stable client-side regex; the gateway applies only a basic syntax check and Google remains authoritative for credential validity. Verify each key's project/service-account binding in Google AI Studio/Cloud before enabling it. The `@google/genai` SDK accepts the key as a string (`apiKey?: string`).

Production startup requires `NODE_ENV=production`, explicit bind/port, TLS Redis (`rediss://`), project, prompt hash, HMAC, at least one enabled valid credential, and explicit quota/timeout settings. TLS certificate verification is always enabled for `rediss://`; set `KIARA_REDIS_CA_CERT_FILE` only when the Redis provider uses a private CA. The client uses a bounded reconnect backoff. See `.env.example` for variable names only; never put production secrets in a local `.env` file.

At startup, the gateway prints redacted preflight checks for configuration, enabled credential slot numbers, HMAC configuration, Redis TLS mode, Redis `PING`, and the HTTP listener. It never prints key/secret values. Credential syntax/configuration is not provider verification, and the gateway does not contact Gemini until a token request; matching the backend's HMAC secret is likewise not independently verifiable by the gateway.

Generate a secret locally with `node -e "console.log(require('node:crypto').randomBytes(48).toString('hex'))"` and set it independently in both services. Compute the prompt hash using the same backend release that will issue requests: `node -e "const c=require('node:crypto'); const {LIVE_SYSTEM_INSTRUCTION}=require('../kiara-server/src/services/live/liveSystemInstruction'); console.log(c.createHash('sha256').update(LIVE_SYSTEM_INSTRUCTION,'utf8').digest('hex'))"`. During prompt rotation, configure comma-separated current and previous hashes, deploy the gateway, then deploy the backend; remove the previous hash after all backend replicas are updated. Do not commit generated secrets.

The gateway path preserves primary-backend admission and metering but adds a network hop. It is not a latency fix by itself; compare token-creation timing and real-session first-response timing in an authorized staging deployment before enabling it in production. No production service or credentials are configured by this source change.

On a provider 401, the affected key fingerprint is disabled in shared Redis for 24 hours and that request stops without trying another key. Later requests select another enabled slot. A key rotation changes its fingerprint; deploy the new key and restart to apply it. Provider 400/403/404/5xx/network errors are not retried across keys. A 429 opens the shared project cooldown and is never retried with another key, since every key belongs to the same Google project. Gateway queue capacity is zero: overload is rejected quickly with `Retry-After`; the primary backend's authenticated account rate limiting and per-account active-session limits remain the user fairness controls.

This service issues connection tokens only. The client-to-Gemini audio/WebSocket connection remains direct, so this gateway does not relay or repair post-connect voice traffic or client network problems. A successful token response is not evidence that the Live WebSocket connected; Kiara verifies and reports that handshake separately.
